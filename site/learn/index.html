A plataforma Hiram, ao vivo.

A palavra não se perde.

Este hub reúne os conceitos que tornam o Hiram uma plataforma multi-tenant de notificações confiável. Abaixo, o caminho ponta a ponta, os dez conceitos e um console para disparar contra a API de verdade, em palco ou ao vivo.

Ponta a ponta

Do POST à entrega, com uma garantia no meio

Uma requisição percorre a plataforma inteira. O que sustenta tudo é a segunda etapa: request e outbox gravados na mesma transação.

  1. Aceitar Hiram.Api · 202

    POST /v1/notifications valida e responde na hora com 202 Accepted. Um Idempotency-Key torna o retry seguro.

  2. Persistir PostgreSQL · uma transação

    O request e a linha de outbox são gravados juntos, ou nada é gravado. Se o commit passou, a mensagem não se perde.

  3. Publicar OutboxRelay → RabbitMQ

    O relé lê o outbox já comprometido e publica a mensagem para o dispatcher, sem perder nada no caminho.

  4. Entregar Dispatcher → SMTP / Resend

    Um pipeline resiliente resolve o provider do tenant, tenta de novo em falha transitória e registra cada tentativa.

  5. Auditar GET /v1/notifications

    Leia de volta o status e a latência de cada tentativa, por paginação de cursor.

Um único trace do OpenTelemetry cobre aceitar, publicar, consumir e enviar.

Os conceitos

Dez ideias que sustentam a entrega

Cada conceito é uma peça vendável do Hiram, aqui com o endpoint ou cabeçalho que o expõe. Verde é o que já roda em produção; o restante está no roadmap público.

01

Outbox transacional

O request e a linha de outbox são gravados na mesma transação. Se o commit passou, a notificação não se perde.

Ao vivoPOST /v1/notifications
02

Idempotência

Um Idempotency-Key colapsa retentativas na mesma entrega por 24 horas, então o retry é sempre seguro.

Ao vivoIdempotency-Key
03

Isolamento multi-tenant

Toda tabela de domínio carrega um tenant desde a primeira migration, com chaves e providers próprios.

Ao vivotenant_id
04

Handshake e chaves

Autentique com uma chave por tenant, guardada só como hash SHA-256 e revogável a qualquer momento.

Ao vivoX-Api-Key
05

Relay e provider

O OutboxRelay publica a mensagem e resolve o provider do tenant, SMTP ou Resend para email.

Ao vivoOutboxRelay
06

Modos live e shadow

Tenants shadow exercem o caminho inteiro e registram um envio, sem entregar de verdade.

Ao vivodelivery_mode
07

Auditoria de entrega

Consulte cada tentativa, com resultado, erro e latência, por paginação de cursor.

Ao vivoGET /v1/notifications
08

Tracing ponta a ponta

Um trace do OpenTelemetry cobre aceite, publicação, consumo e envio em um só fio.

Ao vivotraceparent
09

Console de demonstração

Experimente contra a API

Dois modos: palco, com respostas determinísticas à prova de rede, e ao vivo, que dispara contra a API local na mesma origem. Abaixo, a forma do painel; o console interativo chega com o ADR-021.

POST /v1/notifications
Modo palco: resposta determinística, sem rede.
requisição 
$ curl -X POST http://localhost:3357/v1/notifications \
  -H "X-Api-Key: hk_live_demo…" \
  -H "Idempotency-Key: palco-4207" \
  -d '{"channel":"email","recipient":"loja@tenant.dev",
       "subject":"Pedido confirmado","body":"Seu pedido foi confirmado."}'
resposta · palco 
HTTP/1.1 202 Accepted
{ "id": "ntf_01HZX37V", "status": "accepted" }

O modo palco usa fixtures determinísticas, à prova de rede. O modo ao vivo dispara contra a API local na mesma origem, com a demo key emitida pelo bootstrap. A chave fica só no seu navegador.
